Implementation proposal · Strapi Translate

Translate what changed.
Keep every language connected.

After saving a German page, choose the languages to update, review only the affected modules, and use the matching localized collection items in each translation.

Repository inspected on 12 October 2026. This document proposes implementation; the example below uses sample data.

1. The experience we should build

01 / SELECTIVE TRANSLATION

Save → select languages → preview → apply

A successful save opens a popup when eligible content changed. Show the changed module names and fields, allow multiple target languages, and stage translations for review. Apply only approved changes to target drafts.

02 / LOCALIZED COLLECTION LINKS

Resolve every link in the target language

For each relation in a changed module, check for the linked document’s target-language version. An English page should use the English article when it exists. Show missing translations and draft-only items in the preview.

Recommended default: translate changed fields, preserve untouched target content, and resolve links in the affected modules. Offer a separate selection to translate changes to linked collection items.

Confirmed preference: relink by default and offer linked-item translation as an explicit option. Linked article changes get their own review before they are applied.

1 · Save sourceWait for success.
2 · Choose languagesShow actual scope.
3 · Review modulesText + resolved links.
4 · Apply draftsReport each language.
  • The popup opens once for the user’s completed save. Failed saves, timestamp-only updates, and plugin-generated writes do not trigger it.
  • Display existing translations, missing page locales, pending changes from earlier saves, and relation warnings before starting.
  • Remember language choices per content type. Exclude the source language and languages the editor cannot update.
  • “Later” closes the popup and retains pending changes in a translation side panel. A later save combines unapplied changes for each language.
  • For several changed modules, show a module list and review one module at a time, with a tab for each selected language.
  • For a missing page locale, offer an explicit initial full translation. A small patch cannot reliably create a complete page with required fields.

4. Technical design

The essential design is a persisted change set, stable module mapping, locale-aware relation resolution, and a previewed patch. Expand each part for implementation details.

A. Detect saved changes and retain pending work
  1. Register a Document Service middleware for supported localized content types. Load the deeply populated source draft before an update; call next(); load the saved source afterward. Use a schema-aware canonical representation to compare content. Publish events should follow configured rules and avoid duplicating a prior save.
  2. Ignore managed timestamps and author stamps; retain component IDs separately for matching. Include translatable text, explicit clears, eligible copied fields, relation membership/order, and module insertion/removal/reordering. Never use ctx.params.data alone: it may contain partial values and connect/disconnect operations.
  3. Persist an immutable change record only after the source write succeeds and its transaction commits. Associate it with content type, document, source locale, source revision/hash, acting user, and a save correlation token. A tracking failure must leave the source save intact and surface a retryable translation status.
  4. Maintain an applied source baseline per target language and field/module. Diff the latest source against that baseline when creating a preview. Otherwise, skipping French on one save would lose its earlier pending changes on the next save.
  5. On successful apply, advance baselines only for the accepted operations in that language. Dismissed prompts, excluded fields, failed targets, and discarded previews remain pending. Distinguish “already current” from “pending but deliberately skipped.”

Use dedicated plugin records for change sets, mappings, baselines, and previews, with schema versions, indexes, expiry, and per-record writes. The current whole-store preview object is a reuse point, but concurrent read/modify/write operations need stronger persistence before supporting several editors.

First use: capture future source saves immediately. Existing localized pages need a reviewed module alignment and baseline, or an explicit full translation. Do not infer historical synchronization from matching array positions.

Strapi supports middleware before and after Document Service calls; its documentation places plugin middleware registration in register(). The commit notification and exact admin save observer still require a compatibility spike. Document Service middleware reference

B. Match modules and apply only approved fields

A module means one component or dynamic-zone item. A root field such as the page title gets its own review group. Store logical module keys in plugin metadata, mapping source component identity to the target component identity for each language.

  • Use source component IDs to follow existing modules within that source draft; use a separate mapped target ID when editing the target. IDs are not shared across locales. Persist parent identity and component type, and refresh mappings after writes.
  • Test whether IDs survive save/publish on supported Strapi versions. If a host app already has a stable module UUID, prefer it. If identities are recreated, require explicit alignment or an opt-in stable-key field; avoid guessing from translated content.
  • Represent edits as semantic operations: setField, clearField, insertModule, removeModule, moveModule, and resolveRelation. Address operations by logical identity and field path, using array indices only when serializing the final payload.
  • Traverse only changed translation fields for provider work. A changed rich-text field is translated as one coherent field with its full formatting; other fields remain untouched. Changed empty/null values clear the target explicitly without calling the provider.
  • Start from the fully populated target draft. Apply the selected operations to it, keeping untouched target text, IDs, media, relations, and locale-specific modules. Normalize this merged tree into a writable payload rather than submitting populated read objects directly.
  • For a component array or dynamic zone, Strapi may require the complete merged array in the update. Include the current untouched target items and their target IDs; omit source IDs on inserted items. “Selective” describes which content changes, not necessarily the size of the serialized request.
  • Preview additions, removals, and moves explicitly. Do not delete a target-only module or overwrite a conflicting manual edit automatically. When alignment is ambiguous, ask for module matching inside the review UI.

Respect translate, copy, skip, delete, and regenerate, plus Strapi’s field localization settings. Shared/nonlocalized fields must not be replayed once per locale. Include dependent regenerated slugs in the review if an approved title change would alter them.

C. Resolve linked collection items by language
  1. Collect eligible relations inside each affected module, including unchanged links that need localization. Preserve skip fields. Keep media and nonlocalized collections on their appropriate shared references.
  2. Group localized references by collection type, target locale, and required status. Query all document IDs in a batch and build an availability map. Repeated links should share the lookup.
  3. For article-A linked in German, check the same logical document ID with locale: 'en'. Strapi’s document ID identifies the document across locale variants; the English version generally does not have a different document ID. Do not match by title or translated slug.
  4. Serialize links through a relation adapter using the target locale in the document update and the supported relation syntax for each cardinality. Handle additions, removals, and order, rather than appending every source link. Prove actual resolution in integration tests, including relations nested in components.
  5. Return a human-readable decision for every affected link: source label, target label, document ID, language, status, and proposed action. A manually different target relation becomes an explicit review choice.

Do not retranslate an entire article merely because its parent module’s title changed. Reuse the same selective pipeline and baselines for children; show the effect on all pages sharing the article.

Limit the first release to explicitly selected direct children, deduplicate by collection/document/language, and detect cycles. Apply an approved child first, then its parent relation. A child failure blocks the dependent parent operation while allowing independent targets to finish. Saving an article directly should also expose its own pending translation workflow.

Locale lookups and locale-specific relation writes are documented Strapi features. Nested relation behavior and unsupported/morph relations should be verified or rejected with a clear review message. Locale lookup reference · Relation write reference

D. Stage previews, prevent conflicts, and keep saves predictable
  • Stage one preview per target language in the existing job flow; return 202 { jobId } quickly. Keep cancellation and per-language progress. Existing synchronous single-language preview clients should remain supported.
  • Store approved-scope operations, source snapshot/revision, target fingerprint, identity mapping version, glossary/voice fingerprint, relation resolutions, author, and expiry. Keep the one-hour preview TTL initially.
  • Review source text, current target text, and proposed target text. Provide module cards, field-level selections, full expandable text, relation labels, and separate cards for linked items. Scope excludes all unchanged modules.
  • On apply, recheck permission, current source revision, target content, relation availability, and mapping. A changed source invalidates the preview. A changed target requires rebasing/review; never commit the old full payload over new edits.
  • Validate a transaction/locking strategy in the spike to close the gap between conflict check and write, including manual CMS updates and multiple app instances. If it cannot be made reliable on the declared version range, constrain support before promising conflict protection.
  • Give preview acceptance an idempotency key and record its result atomically with baseline advancement. Retrying after a network failure must not insert modules twice. Lock or version preview records against simultaneous accept requests.
  • Keep commits atomic per page/locale; show partial success across languages and dependent documents. Retry failed work only. Reuse validation repair for approved text, but if repair changes a staged translation, return the repaired preview for review before applying it.
  • Recheck read/write permissions for the parent, linked content, relevant fields, and allowed languages. Preserve creator metadata, stamp the current acting editor appropriately, and use operation provenance to suppress recursive prompts/auto-jobs across instances.

Apply to drafts where Draft & Publish is enabled; publication remains a separate action. For content types without drafts, saving immediately affects live content, so the review must clearly name that effect.

Preview scope: the first release renders the module’s content inside the CMS. An exact website preview requires a host frontend renderer/preview integration; the plugin does not have each site’s component templates.

E. Connect the admin UI and API

Add a mounted Edit View panel/observer alongside the document action. Detect the current user’s successful save from the supported refreshed document state or hook for the tested Strapi version, and request the matching persisted change set. Deduplicate by save token/revision, not by every render or poll. Keep a “Pending translation changes” panel for dismissed prompts and changes made through the API.

Strapi exposes document actions and Edit View side panels. Its documented extension API does not establish a universal after-save event; verify the observer integration before committing to a version range. Content Manager extension reference

6. Acceptance criteria

One field edit: only that field reaches the provider; only its approved target value changes.

Multiple languages: select English and French, review each independently, and apply only chosen drafts.

Existing manual translations: untouched text, relations, media, IDs, and target-only modules survive the merge.

Module structure: insertion, deletion, reordering, nested modules, and duplicate component types map correctly.

Linked articles: the English page resolves the English article with the same logical document ID.

Missing language: optional links need an explicit reviewed fallback; unresolved required links block acceptance.

Pending changes: a skipped language receives earlier unapplied edits on a later run; excluded fields stay pending.

Concurrent edits: a changed source/target invalidates or rebases the preview; retries cannot duplicate modules.

Edge values: clears and relation-only changes work without unnecessary AI calls; formatting and constraints survive.

Permissions and recursion: parent/child permissions are enforced; translation writes never prompt or enqueue themselves again.

Jobs: cancellation, restart, expired previews, partial language failure, and child failure offer a recoverable outcome.

Publication: draft workflows keep publication separate; draft-only linked items are visible as warnings.

Extend tests/services/translate.test.js, preview.test.js, translatable-fields.test.js, auto-translate.test.js, and controller tests. Add focused tests for changes/mapping/relations, plus real Strapi integration and admin workflow checks. Existing mocks alone cannot verify locale resolution or component persistence.

7. Decisions and boundaries

Proposed product defaults: prompt after a successful source save; translate changed fields; select languages explicitly; require preview; apply to drafts; relink existing localized collection items; offer linked-item translation as an explicit selection.

Implementation gates: supported Strapi version and save observer; stable module identity/alignment strategy; atomic conflict checking; missing-link policy for each schema. The spike should settle these before broad rollout.

Frontend delivery: this plugin updates CMS content. If the website caches pages or uses static builds, publishing/revalidation must use the host site’s integration. Updating only one visible site module may require targeted cache invalidation outside the plugin.

Evidence: current behavior comes from the repository files listed above. API capabilities were checked against official middleware, locale, relation, and Content Manager documentation. Architecture, estimates, and defaults are recommendations, not claims that the features already exist.
